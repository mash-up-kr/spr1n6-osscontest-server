# 코드 컨벤션 점검

## 목적

여러 사람이 각자 구현한 파트를 하나의 프로젝트로 읽히게 만든다. 평가 항목인 **코드의 가독성 · 주석의 활용도 · 구조의 합리성**을 기준으로 점검한다.

동작을 바꾸는 것이 목적이 아니다. 결함을 발견하면 보고만 하고 고치지 않는다.

## 기준

`docs/CODE_CONVENTIONS.md`를 유일한 기준으로 사용한다. 이 파일을 **먼저 읽고 시작한다.** 없으면 점검을 진행하지 말고, 어느 저장소에 있는지와 파일이 없다는 사실을 보고한다.

## 1단계 — 대상 파악

먼저 이 파트가 무엇을 하는 코드인지 파악한다.

- 이 파트가 프로젝트에서 맡은 역할은 무엇인가
- 어떤 언어·프레임워크인가
- 어느 파트와 무엇을 주고받는가 (DB 스키마, 이벤트 형식, API)

## 2단계 — 범위 정하기

사용자가 범위를 지정하지 않았으면 **파트 전체**를 대상으로 한다. 제출 전 정리는 변경분만 보는 것으로 부족하다.

파일이 많으면 진입점과 핵심 로직부터 읽고, 읽지 못한 범위를 결과에 명시한다. **읽지 않은 파일을 읽은 것처럼 보고하지 않는다.**

## 3단계 — 주석 점검

주석을 줄이는 것이 목적이 아니다. **역할에 맞는 주석이 제자리에 있는지**를 본다. 주석 하나마다 길잡이·계약·근거 중 어느 역할인지 판별하고, 셋 중 어느 것도 아니면 지울 대상으로 분류한다.

**채울 것** — 이 항목을 먼저 본다. 없어서 안 보이는 문제라 놓치기 쉽다

- 흐름이 긴 함수에 단계를 끊어 주는 길잡이 주석이 없는 경우
- 공개 함수에 호출자가 알아야 할 제약이 안 적힌 경우
- 근거 없는 숫자 (타임아웃, 상한, 크기, 재시도 횟수)
- 왜 그렇게 했는지 알 수 없는 분기나 우회
- 다른 파트의 계약에 기대는데 소유자가 안 적힌 코드
- 코드를 그대로 읽으면 오해하게 되는 지점

**지울 것**

- 코드 한 줄을 그대로 옮긴 주석. 덩어리를 요약하는 길잡이 주석은 여기 해당하지 않는다
- 주석 처리된 코드
- 주인도 기한도 없는 TODO/FIXME
- 설명 없는 자동 생성 문서 주석
- 변경 이력, 구분선 장식

**고칠 것**

- **코드와 어긋난 주석** — 가장 먼저 보고한다. 읽는 사람을 틀린 방향으로 보낸다
- 너무 길어 읽히지 않는 주석
- 여러 판단을 한 덩어리에 몰아 쓴 주석

**문체**

- 평서형 단정체(`~한다`)로 통일됐는지 확인한다. 존댓말과 구어체를 찾아 고친다
- 길잡이 주석이 요약형 명사구(`~조회`, `~검증`)인지 확인한다
- `~할 수도 있다`, `~하는 게 좋을 것 같다` 같은 완곡 표현을 찾아 단정형으로 고친다

## 4단계 — 가독성 점검

1. 이름이 역할을 말하는가. 함수 이름의 동사가 실제 행위와 맞는가
2. 공통 개념을 컨벤션 문서의 용어표대로 부르는가. 파트마다 다르게 부르는 이름이 있는가
3. 한 함수가 한 가지 일을 하는가. 한 함수 안에서 추상화 수준이 섞이지 않는가
4. 중첩이 깊은 곳을 early return 으로 평평하게 만들 수 있는가
5. 매직 넘버가 코드에 박혀 있지 않은가
6. 하드코딩된 주소·경로·자격증명이 없는가
7. 안 쓰는 코드, 도달할 수 없는 분기, 안 쓰는 import 가 남아 있지 않은가

## 5단계 — 구조 점검

1. 입출력 / 업무 / 저장 역할이 섞이지 않았는가
2. 남이 소유한 스키마나 계약을 이 파트에서 고치고 있지 않은가
3. 서로를 부르는 의존이 없는가
4. 같은 로직이 세 번 이상 반복되지 않는가
5. 파일 하나가 여러 관심사를 담고 있지 않은가

## 6단계 — 실패 처리 점검

1. 외부 경계에서 빈 값과 기본값을 구분하는가
2. 조건이 어긋났을 때 오류 대신 "결과 0건"으로 끝나는 경로가 없는가
3. 삼킨 예외에 이유가 적혀 있는가

## 하지 않을 것

- **동작을 바꾸지 않는다.** 로직 수정이 필요하면 보고만 한다
- **대량 리포맷을 하지 않는다.** 들여쓰기·줄바꿈 스타일을 통째로 바꾸면 diff 가 폭발해 리뷰가 불가능해진다
- 컨벤션에 근거가 없는 취향을 규칙인 것처럼 말하지 않는다
- 의도가 있어 보이는 설계를 확인 없이 결함으로 단정하지 않는다

## 결과 작성

아래 형식으로 쓴다.

```
## 점검 범위
- 파트: (역할 한 줄)
- 읽은 파일: N개 / 전체 M개
- 읽지 못한 범위: (있으면)

## 지금 고쳐야 할 것
1. {파일}:{줄} — {무엇이 잘못됐는지}
   그대로 두면: {무엇이 깨지거나 오해되는지}
   고칠 방향: {구체적으로}

## 정리하면 좋은 것
(같은 형식, 우선순위 낮음)

## 채워야 할 주석
- {파일}:{줄} — {어떤 근거가 빠졌는지}

## 판단이 필요한 것
- {컨벤션으로 결정할 수 없어 담당자가 정해야 하는 것}
```

- **코드와 어긋난 주석**과 **조용히 틀리는 경로**를 항상 맨 위에 둔다
- 각 항목에 파일과 줄 번호를 붙인다
- 규칙 위반과 취향 차이를 섞지 않는다
- 문제가 없으면 확인한 범위와 남은 위험을 간단히 적는다

## 고치기

사용자가 수정까지 요청하면 아래를 지킨다.

- 주석 정리, 이름 변경, 죽은 코드 삭제까지만 한다
- 로직을 바꾸지 않는다
- 정리 커밋과 동작 변경 커밋을 섞지 않는다
- 수정 후 빌드와 테스트를 돌려 결과를 함께 보고한다. 돌리지 못했으면 그 사실을 적는다
